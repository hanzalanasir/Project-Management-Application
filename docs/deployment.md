# Deployment (IIS on Windows Server)

Per Constitution XI: the API is published as a self-contained deployment; the Angular app is
built for production and served **same-origin** by the API (ADR-0002) — this is what lets the
refresh cookie use `SameSite=Strict` in every environment, since there is no cross-origin request
to protect against.

## 1. Build the Angular app into the API's `wwwroot/`

```powershell
cd src/ProjectManagementApp.Web
npm ci
npm run build -- --configuration production
```

The production build configuration's `outputPath` is set to
`../ProjectManagementApp.Api/wwwroot` (see `angular.json`), so this step populates the API
project's static files directly — no manual copy step.

## 2. Publish the API as a self-contained deployment

```powershell
cd src/ProjectManagementApp.Api
dotnet publish -c Release -r win-x64 --self-contained true -o ./publish
```

This bundles the .NET runtime with the app — the target IIS server does not need the .NET 10
runtime installed separately, only the [ASP.NET Core Hosting Bundle](https://dotnet.microsoft.com/download/dotnet/10.0)
for the in-process IIS module.

## 3. IIS site configuration

1. Create a new IIS site (or application) pointing its physical path at the `publish/` folder.
2. Set the Application Pool's **.NET CLR version** to **No Managed Code** (the self-contained
   app hosts its own runtime via the ASP.NET Core Module).
3. Ensure the `web.config` generated by `dotnet publish` is present in the site root (it wires
   up the ASP.NET Core Module automatically).
4. Bind HTTPS with a valid certificate — the refresh cookie requires `Secure`, and the app's
   `UseHttpsRedirection()` expects TLS to terminate at (or in front of) this site.

## 4. Environment-specific configuration

Hardcoded environment values are prohibited (Constitution XI.2). Configure per environment via:

- **Backend** — `appsettings.{Environment}.json` alongside the published output, or environment
  variables (`ASPNETCORE_ENVIRONMENT`, `ConnectionStrings__DefaultConnection`,
  `Jwt__SigningKey`, `Seed__Enabled=false` in production, etc.). Set `ASPNETCORE_ENVIRONMENT` in
  the IIS Application Pool's environment variables or the site's `web.config`.
- **Secrets** (`Jwt:SigningKey`, the connection string) — **never** committed; set as
  machine-level environment variables or via a secret store. `Program.cs` fails fast at startup
  if either is missing.
- **Frontend** — the Angular build has no separate runtime environment file in this project (the
  API serves it same-origin, so there is no API base URL to configure per environment); any future
  environment-specific frontend values belong in `environment.{name}.ts` per Constitution XI.2.

## 5. Database

Apply migrations against the production database before or during first deployment:

```powershell
cd src/ProjectManagementApp.Infrastructure
dotnet ef database update --project . --startup-project . --connection "<production-connection-string>"
```

(Alternatively, `Program.cs` calls `db.Database.MigrateAsync()` at startup automatically, so a
first request after deployment applies any pending migration.) Set `Seed:Enabled=false` in
production — seeding is a development convenience only.

## 6. Verification checklist

- [ ] `GET /api/health` returns 200 over HTTPS.
- [ ] The Angular app loads at the site root and API calls resolve same-origin (no CORS errors —
      `Cors:AllowedOrigins` is inert under same-origin deployment, but leave it empty/explicit
      regardless per Constitution V.6).
- [ ] Register → log in → refresh → logout all work end-to-end (quickstart.md V1–V14).
- [ ] No secret value appears in `appsettings.json`/`appsettings.Production.json` committed to
      source control.
